공개 페이지 이미지 품질 감사

대상 13개 페이지(홈, 인사이트 목록, 기사 3개, Brand Watch·MUSINSA, Career Lab, Insight Lab, Trend Quiz, AI Interview, Weekly, About) × 1440px@2x · 390px@3x. headless Chrome에서 보이는 모든 img를 수집하고, 브라우저가 실제로 받은 파일과 원본 파일을 각각 내려받아 픽셀 크기를 쟀습니다. 운영 이미지는 바꾸지 않았습니다.

판정 기준

  • 선명도(eff) = 화면의 기기 픽셀 1개에 원본 픽셀이 몇 개 대응하는가. object-fit: cover로 잘리는 부분까지 반영하고, 전달 파일과 원본 중 작은 쪽을 기준으로 합니다. weserv는 기본값이 확대 허용이라, 전달 파일이 커도 원본이 작으면 원본 크기로 계산합니다.
  • A 정상: 해당 기기 배율에서 eff ≥ 0.9 · B 개선 권장: 1배율에서는 충분하지만 레티나에서 부족 · C 교체 필요: 1배율에서도 확대되거나 로딩 실패 · D 원본·이용 권한 확인 필요: A가 아닌데 권리 기록이 없는 외부 이미지(수집 기사 대표 이미지)
  • 파일 크기가 작다는 이유만으로 저화질로 판정하지 않았습니다(예: 2KB 썸네일도 eff ≥ 0.9이면 A). SVG는 해상도 무관으로 A.

핵심 원인

  • 1. 수집 단계가 매체의 축소판 URL을 저장 — A가 아닌 33건 중 30건. Adweek는 ?w=600&h=315&crop=1, Campaign Brief(WordPress)는 -1024x565.jpg 같은 축소판을 기사 대표 이미지로 저장합니다. 같은 매체 서버에 원본이 있습니다(600×315 → 1200×675~6000×4000, 1024 → 1200~1500). 화면이 커질수록 흐려집니다: 기사 상세 대표(1320px 폭)·홈 Collections·Latest 대표.
  • 2. 목록 썸네일의 sizes가 크롭을 고려하지 않음 — 96×83 상자(390)와 280×181 상자(1440)는 1.91:1 원본보다 세로가 길어, 높이를 채우려면 상자 폭보다 넓은 원본이 필요합니다. 기존 sizes는 상자 폭만 알려 줘 브라우저가 320px(390@3x)·640px(1440@2x)을 고릅니다. 로컬 수정 완료: sizes를 높이 기준 폭(160/248/346px)으로 바꿔 실제 Chrome에서 480px·768px을 고르는 것을 확인했습니다(src/components/insights/EditorialInsight.tsx).
  • 3. 자체 자산 — 홈 Hero(1440@2x에서 1920px이 최대, B)와 Brand Watch MUSINSA 로고(243×60 PNG를 259×64로 확대, C). BAEMIN 로고도 같은 방식(284×64 → 표시 높이 72)입니다.
  • 로딩 실패 0건, 사진 속 글자 깨짐은 축소판 확대가 원인인 경우(월마트 앱 화면 캡처 등)에서만 보였습니다. 과한 보정은 발견하지 못했습니다.

전후 비교

각 상자는 표시 영역을 기기 픽셀 1:1로 확대해 가운데를 잘라 보여 줍니다(레티나 화면에서 보이는 실제 밀도). “후보”는 같은 매체 서버의 원본을 같은 CDN·같은 폭으로 받은 결과로, 운영에는 반영하지 않았습니다.
